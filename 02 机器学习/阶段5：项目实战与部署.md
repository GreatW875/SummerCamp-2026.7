## 模块 1：完整项目流程串讲

**需求 → 数据 → 特征 → 模型 → 评估**

> 类比开餐馆：需求=定菜品，数据=买食材，特征=洗菜切配，模型=下锅烹饪，评估=试吃验收。

### 五步流程 ↔ 已学知识对照

| 流程 | 干什么 | 对应已学知识点 | 头号大坑 |
|---|---|---|---|
| **需求** | 把"人话"翻译成"机器话"：定 y、定分类/回归、定成功指标 | 问题定义、评估指标选取（本阶段新能力） | 方向错，后面全白干 |
| **数据** | 收集 → EDA 体检 → 划分 | 探索性数据分析（EDA）、缺失值插补、异常值处理、数据泄漏防护 | 泄漏——预处理必须进 `Pipeline` |
| **特征** | 把原料处理成"能下锅"的状态 | One-hot / Target Encoding、Box-Cox 变换、特征构造与交互、RFE 特征选择、`Pipeline` | 只换模型不造特征（特征决定上限） |
| **模型** | 先基线打底，再升级 | 逻辑回归（基线）、随机森林、XGBoost、LightGBM、Stacking | 盲目调参（调参是最后一步） |
| **评估** | 打分 + 诊断 + 归因 | 混淆矩阵、ROC-AUC / PR-AUC、StratifiedKFold 交叉验证、学习曲线诊断、错误分析 | 不平衡数据只看 Accuracy |

**核心认知**：这不是单向流水线，而是**循环**——评估结论会把你打回前面某一步（欠拟合→回特征/模型，数据问题→回数据），迭代几圈才收敛。上线后再补"监控"环节，发现漂移就回到数据重新迭代，形成完整闭环。

## 模块 2：模型优化与解释

**调参 + SHAP + 错误分析**

> 三件事回答三个问题：模型还能不能更好（调参）、为什么这么预测（SHAP）、在哪里会犯错（错误分析）。

| 手段 | 核心思想 | 类比 | 关键要点 |
|---|---|---|---|
| **Optuna 调参** | 根据上次结果，聪明地选下一组参数 | 调洗澡水温，不是瞎拧每个刻度 | 诊断先行：学习曲线判欠拟合/过拟合再定方向；≥50 trials、固定 `random_state` |
| **SHAP 解释** | 算每个特征对本次预测的贡献（可正可负） | 团队分奖金：看你"在与不在"差多少 | 全局看 summary 蜂群图、局部看 waterfall 图；兼作数据泄漏探测器（ID 类特征排第一=警报） |
| **错误分析** | 挑出错样本人工归因 | 学霸的错题本 | 三方向：特征不够→回特征工程；噪声/标注错→洗数据；边界本身模糊→接受天花板 |

**工作流**：基线 → 学习曲线诊断 → Optuna 调参 → SHAP 检查合理性 → 错误分析归因 → 回流特征/数据 → 再迭代。

**产出物**：一页模型报告（指标 + 学习曲线 + SHAP 图 + 错误样本分析）。

## 模块 3：模型持久化（Joblib）与 FastAPI 服务化

> Joblib 解决"模型怎么存"，FastAPI 解决"别人怎么用"。
> 类比：训练=培养厨师（耗时），Joblib=把手艺冷冻保存、解冻即用，FastAPI=开点餐窗口——递 JSON 单子进去，端预测结果出来。

### Joblib 持久化

- 核心两行：`joblib.dump(model, 'model.pkl')` 存 / `joblib.load('model.pkl')` 取
- **存的是整个 `Pipeline`**（预处理 + 模型打包），保证线上预处理与训练时一致
- 选 Joblib 而非 Pickle：模型本质是大量 NumPy 数组参数，Joblib 对大数组存取更快

### FastAPI 服务化三零件

| 零件 | 干什么 | 类比 |
|---|---|---|
| `@app.post("/predict")` | 定义接口地址 | 点餐窗口 |
| Pydantic 模型 `Input` | 校验传入 JSON 的字段与类型，不合规返回 422 | 门口安检，脏数据进不了厨房 |
| 返回 `{"prediction": ...}` | 输出预测结果 | 出菜 |

- 附赠亮点：访问 `/docs` 自动生成交互式文档页面，可现场试点
- 联调测试：`fastapi dev main.py` 起服务 → curl / Postman 发 JSON → 核对返回

### 完整链路

训练 → dump 存 Pipeline → API 启动时 load 一次（常驻内存）→ 收 JSON → Pydantic 安检 → 转 DataFrame 对齐特征名 → `pipeline.predict` → 返回 JSON

**性能要点**：模型在服务启动时 load 一次，不是每来一单才解冻——开门前备好菜，营业时只管炒。

## 模块 4：Docker 容器化与项目文档

> Docker 让项目在任何地方都能跑，文档让别人看得懂能复现，复盘让收获真正属于自己。

### Docker：把整间厨房打包寄走

- **解决痛点**："在我电脑上明明能跑啊！"——Docker 把代码 + 环境（Python 版本、依赖库）整体打包成集装箱，任何机器拆开即用
- **三件套**：`Dockerfile`（装修图纸）→ build → 镜像 Image（样板房）→ run → 容器 Container（营业中的房子）

**Dockerfile 六行骨架**：

```dockerfile
FROM python:3.10-slim            # 毛坯房：带 Python 的精简系统
WORKDIR /app                     # 进屋定工作目录
COPY requirements.txt .          # 先搬清单（利用构建缓存）
RUN pip install -r requirements.txt   # 按清单装修
COPY . .                         # 再搬家具（全部代码）
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]  # 点火开业
```

- **两条命令**：`docker build -t 名字 .` 造镜像 → `docker run -p 8000:8000 名字` 起容器（端口映射 = 大堂 8000 号窗口对应后厨 8000 号灶台）
